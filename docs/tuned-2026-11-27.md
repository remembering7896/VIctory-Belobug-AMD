# Tuned run: what was measured (2026-11-27)

One PC: Ryzen 7 9800X3D, 32 GB RAM, Radeon RX 7900 XTX 24 GB, Windows 11
build 26300, Series X profile at 1080p output, ray tracing off. Builds are
`cargo build --locked --profile diag -p victory --features diagnostics`.
Every run is the same sequence from a cold start, 6-10 minutes, and the
figures are of the `host: … fps, … ms/frame` line the runtime prints.

Scenes are not identical between runs; read differences under about 5 % as
nothing. The numbers below repeat across runs, which is why they are kept.

## Where the time went

| Build and settings | p50 frame | p50 fps | p90 frame |
|---|---|---|---|
| original tree, default switches | 59.0 ms | 17.0 | 103.3 ms |
| + the memory patches of this branch | 58.3 ms | 17.4 | 72.5 ms |
| + the renderer port switches (below) | **46.2 ms** | **21.9** | 86.6 ms |

The port switches are the ones `README.md` lists as off by default while
they are tested. Turning them on is worth about 15 ms a frame, more than
every memory patch in this branch together. In the log the preparing
thread goes from 42-52 ms to 28.9 ms a frame: `VICTORY_PORT_CBV` removes
about 22,000 constant-buffer fills a frame, `VICTORY_PORT_GUARD` takes the
title threads' guard waits from 29 ms to about 2 ms, `VICTORY_PORT_JOURNAL`
takes the submit thread's waits from about 6 ms to 0.3 ms.

`scripts/run-tuned.bat` starts the title with them on.

## What was tried and refused

Each was applied on top of the winning tree, built, and run the same way.
All three are worse here, whatever they win elsewhere:

| Change | p50 frame | p50 fps |
|---|---|---|
| Belobug #443 + #451 (exact/loose lock contention) + #393 (tiled mip row runs) | 53.8 ms | 18.6 |
| Belobug #394 (32 GB switch set) + avatarmanz #391 (`VICTORY_WINDOWS_BAR_PCT`) | 51.5 ms | 19.4 |

A first attempt that also carried #393 and #374 in the same commit as the

patches are only added to the tree after a run in this table.

## Pipelines made ahead of a run

A pipeline the driver has not seen costs 2.7 ms at the median to make but
533 ms at the p99, and that lands in the game as one long frame. One
recording run (`VICTORY_PIPELINE_BOOK=1`, five minutes) wrote down 3,780
pipelines that had been drawn with; `victory warm --used` made them in
26 s of wall time and 82 s of compiler work, nothing else. The run after
it built **none** while playing, where the run before had up to 176 of
them in flight, and the log's `being made` counter stayed at 0.

It does not move the steady frame time: what is left of a 46 ms frame is
the submitting thread, not compilation. What it removes is the tail - the
single 400-570 ms frames that a first visit to new geometry produces.
Coverage is only what a run has recorded, so a part of the title played
for the first time still compiles as it goes: run `scripts\warm-tuned.bat
record` once there, which plays a run with the book on and then warms.

`scripts\warm-tuned.bat` does both, with the same switches as
`scripts\run-tuned.bat` - the cache is keyed by a pipeline fingerprint
(`e9cc66c4ece2c90a` here), so warming under different switches fills the
cache with pipelines the next run will not ask for.

## 60 Hz

`VICTORY_FRAME_INTERVAL_MS=16.667` does what it says: the menus and videos
reach 55-60 fps (best frame 16.7 ms) and the log confirms the clock is
adjusted (`our clock 16.667 ms; the title's rate 60 … it asks for 16667 us
at 60 Hz`). In the world it costs about 9 ms a frame (median 55.4 ms
instead of 46.2), because twice as many submissions queue on the one
submitting thread. Not used by `scripts/run-tuned.bat`.

## Memory

The eleven patches in this branch reclaim idle upload memory and cap the
texture store; on this 32 GB PC the peak private bytes went from about
38 GB to about 36-37 GB, and the p10 frame improved from 9.7 to 13.8 fps
(fewer long stalls). The pressure thresholds these checks use are only
reached when the machine is short of RAM, so a 32 GB box shows much less
of the effect than the 16 GB reports in the pull requests.

The eleven, all from `Belobug/VIctory-Belobug-AMD` with `base=a-publier`:
#386, #404, #373, #372, #375, #359, #287, #409, #413, #401, #407.

## The benchmark that makes these numbers judgeable

Free runs are not comparable: the same settings gave 40.7 ms one run and
49.1 ms the next, and the same settings drifted 2.4 ms between sessions
(43.1 one session, 40.7 the next). `bench.ps1` and `pad-replay.py` (in
`D:\victory-belobug`, not in this repository) fix that:

- every run launches the title, waits 15 s, presses A on a virtual Xbox pad
  (ViGEmBus) to leave the menu, and waits for the world: frame lines with
  1500 or more draws, twice in a row;
- then it plays the same 10 s input cycle (walk 3 s, stand 1 s, pan right 2 s,
  walk and pan 3 s, stand 1 s) for a whole number of cycles, and takes only
  the frame lines inside that window;
- three runs of one arm spread 1.2-1.7 ms, so an effect has to be larger
  than that to be worth anything;
- arms are compared *inside one session*, alternating (A, B, A, B): session
  drift is larger than every effect measured here.

## Ported from Yaekai/victory-scarlett-3070, and what came of it

`VICTORY_CARD_LISTS=1` (foxhound 441446d, through that fork's bc264a4): the
copies in the card's memory whose CPU side changed are taken from a list made
as they are touched, instead of being found by a walk over every copy
(`crates/victory-gpu/src/shadow.rs`: `carded`, `TOUCHED`, `card_dirty_listed`).
Off by default.

Measured: frame 43.8 vs 43.1 ms (-0.6, inside the noise), copies 10.0 vs
10.1 ms. The list does what it says (the touch list is walked, not the whole
table), but the walk was never the cost: this branch's own counter line shows
95 hash passes over 415 pieces on the plain path, not the 348 over 2,080 seen
in an earlier, heavier scene. Left in the source, off, like that fork's other
"built, exact, no gain shown" switches.

Read from the same fork and not taken:
- `VICTORY_WINDOWS_BAR_MB` (the title's memory read through Resizable BAR):
  it reports no gain while the card stands idle, plus 1.4 GB of VRAM. That is
  this branch's situation too, so the "copy less by mapping it" road is closed
  before it is walked.
- `VICTORY_LEVELS_ON_DEMAND`: its launcher sets it to 0 and calls it the
  largest single gain (re-uploads 6.4 GB -> 15 MB, about 4 GB less commit).
  This branch is already off by default, which is the same setting.
- `VICTORY_TABLE_MEMO` (81 % of about 54,000 table entries a frame not built
  again) and `VICTORY_TABLE_NAMED_ONLY` (27,000 slots a frame less): both live
  inside a 1,150-line commit over `draw.rs`, far from this tree's lineage. The
  ceiling here is the 3.28 ms a frame the descriptor records cost, so the port
  is worth nothing like its size.
- `VICTORY_SOFT_VIEWS=copies`: the one still worth having. It keeps the views
  the title's batch page-mapping copies make in the layer's books and maps them
  only when touched (264 lines over `shadow.rs`, `resource.rs`, `host.rs`); that
  fork went from 2.7 % to 0.8 % long frames and from 10-12 to 3 five-second
  freezes. This branch's own stall was 4.5 s of preparing, once, followed by a
  removed device.

## Soft views: what is built, and what the second half must not miss

`crates/victory-gpu/src/soft.rs` holds the books: `noted`, `real`, `gone`,
`read`, a bit a 64 KiB block in `watch::Bits`, and `VICTORY_SOFT_VIEWS`
(`0` off, `copies`, `verify`). `host::read_into` asks them first and falls
through. Nothing notes a view yet, so the switch does nothing: it is in the
tree to be wired, and it compiles and costs one atomic load a read.

The wiring is worth its risk only if it keeps three things `xmem::map` does
beside the kernel call, which a plain "skip the map" port would drop:

- `shown_mut().note(base, len, &slice)`, so DirectStorage writes that landed
  earlier at those addresses are there when the copies of them run;
- `title_memory_remapped(base, len)`, so the GPU side stops guarding it;
- `title_memory_view(base, len, section, offset)`, the in-place census of what
  a range shows.

Each of them has to move to the moment a soft view is made real, not be
skipped with the map. Anything that reads a soft page before that (the guard
pass, the texture refresh, the copy-back) has to go through `soft::read`.

Second: the source. `Physical::views: HashMap<base, (len, Slice)>` already
knows, per view range, which section and which page it shows; a soft view is
exactly the case where it must keep that record while the kernel mapping is
gone. So the book is target page -> source page, and `Books::read` takes both.

Third, and the reason this can be safe at all: `CopyPageMappingsBatchX` aliases
pages, it does not copy them. Both addresses show one set of bytes, so a write
through the view is a write through the source: no copy on write, no read-only
bit needed. If a later title ever asks for a private page there, the soft
view has to be made real before the write, which is a different patch.

Writes that fault on a soft page must make it real in the fault handler, the
same as reads, and the handler's abort path for `crate::safecopy` must keep
working: a copy that took the fault is failed, not continued.

### The one thing that must be settled before the fault handler is touched

Making a soft page real inside the access-violation handler means taking
`PHYSICAL` (a `std::sync::Mutex`, not reentrant) from the faulting thread. The
title's own calls already hold it: `XMemMapPhysicalPages` at `xmem.rs:1270`,
`map_alias` at 1361, the two batch loops at 1432 and 1458. And the code at 1270
says so itself, in a comment: a read of title memory in place must not fall
into the gap while a view is unmapped and mapped again.

So the two orders are both live in that tree: a thread holding `PHYSICAL` that
touches a soft page deadlocks on itself. `try_lock` alone is not an answer
either: the fault cannot be failed, the instruction has to run.

The shape that works, and is what the 3070 fork's `soft_make_real` amounts to:
the faulting thread parks on a page-sized latch, a thread that can take
`PHYSICAL` maps the page (or finds it already mapped), and the faulting thread
is woken and the instruction retried. Bounded, no lock held across the park,
and a timeout turns a deadlock into a reported failure instead of a freeze.

Writing that is the next piece of work. Until it exists, `VICTORY_SOFT_VIEWS`
must stay `0`: noting a view without a way to make it real is a crash on the
first read of it, not a saving.

### Soft views, tried: it crashes, and the log says why

The wiring is in (noting in `map_alias`/`map_aliases`, release in `unmap`, a
`Books` impl that reads a page through the section's kept view, the fault
handler asking the maker thread). Turned on for one run, it crashed before the
world, and said two separate things on the way:

1. `a soft page was not made real in time: a thread holding the title's views
   asked for it itself` — three times, then the crash reporter. So the
   self-deadlock is not a corner case: the title's own paths read title memory
   while holding `PHYSICAL` (the gap `XMemMapPhysicalPages` worries about in its
   own comment). A maker thread cannot help a thread that holds the lock the
   maker needs.
2. `mapping physical pages failed (not a placeholder?)` at the address that was
   just unmapped: after `unmap`, the range is a hole, not a placeholder, so
   mapping it again later is not the same call as mapping it in the first place.
   Noting a view therefore cannot be "unmap now, map later".

Both point one way: the fault handler must map **without `PHYSICAL`**, straight
from the section (`MapViewOfFile3` over `MEM_REPLACE_PLACEHOLDER` needs the
section handle and the page index, not the view table), and the book has to
keep the section alive per noted page — that is, a `Slice`, opaque to
`victory-gpu`. Then the table is only told afterwards, off the fault path, and
the hole problem goes away because nothing is unmapped before it is needed.

Until that exists `VICTORY_SOFT_VIEWS` stays `0`, and the deployed build in
`D:\victory-belobug\VIctory-Belobug-AMD-main` is the pre-soft one.

### Second try: the deadlock is gone, the mapping is not

Pins instead of a maker thread: every noted page carries its section and page
index, reads go through the section's kept view, and a fault asks the pin for
`MapViewOfFile3` with `MEM_REPLACE_PLACEHOLDER` -- no lock on the fault path at
all. The `not made real in time` line is gone: nothing waits on `PHYSICAL` any
more, so a thread holding the view table no longer deadlocks.

What it says now, at the first touched page: `a soft page could not be mapped
at=0xb43180000`, twice, then the crash reporter. `MapViewOfFile3` refused at
the address. Two candidates, and the next run must print
`std::io::Error::last_os_error()` beside the address to tell them apart:

- the address is not a placeholder any more. `unmap` uses
  `UnmapViewOfFile2(MEM_PRESERVE_PLACEHOLDER)`, so it should be one -- unless
  the page was mapped by a pin whose `Physical::views` insert was skipped
  (`try_lock` busy), and a later `unmap` then could not find the view to
  preserve its placeholder.
- the section is 64 KiB paged (`PAGES_64K`), and `MEM_REPLACE_PLACEHOLDER`
  wants the address aligned to the section's page size and the range inside the
  placeholder exactly.

Either way the missing piece is the same: a pin that maps must also be
recorded, so the next `unmap` can preserve what is there. That record cannot be
`Physical::views` under `try_lock` on the fault path; it has to be a lock of
its own that both the fault path and `unmap` take, cheap and never held across
a kernel call.

### Third try: the address is not a placeholder, and the error says so

`last_os_error()` on the refused mapping: **487, `ERROR_INVALID_ADDRESS`**. So
`MapViewOfFile3(MEM_REPLACE_PLACEHOLDER)` is being pointed at a range that is
not a placeholder at all, and one thing explains that: the placeholder was
never ours. `unmap` preserves a placeholder with
`UnmapViewOfFile2(MEM_PRESERVE_PLACEHOLDER)`, but preserving only works for
views that sit inside a placeholder someone kept; where the title's own
mapping sat on a plain reservation, its unmap leaves nothing behind, and 487
is exactly what mapping into that leaves.

The fix is to stop depending on what the title's unmap leaves. At note time,
replace the range with a placeholder we make ourselves:
`VirtualAlloc2(..., MEM_REPLACE_PLACEHOLDER, PAGE_READWRITE)` over the whole
range, once per range rather than once a page, which is what a soft view is
supposed to cost. Then every address a pin may map is a placeholder by
construction, and `MEM_PRESERVE_PLACEHOLDER` on the way out keeps it that way.

`taken`/`made` in `soft` are the other half and stay: a page a pin mapped has
to be known to `unmap` even when the title's view table never learned of it.

### Fourth try: what the range is, and the split that fixed most of it

`VirtualQuery` at note time, twelve samples, all the same shape:

    to=0xb40000000 len=65536 region=state=0x2000 type=0x20000 protect=0x0 alloc=0x700000000 region=0x1c0000000

`MEM_RESERVE | MEM_PRIVATE`, a plain reservation inside a 7 GB one. So the
addresses were never placeholders of ours to put a view back into, and the
first attempt to reserve them as placeholders was wrong twice over
(`VirtualFree(MEM_RELEASE)` cannot cut a slice out of a plain reservation, and
`VirtualAlloc2` cannot reserve over a placeholder).

What is actually there is a placeholder that is **longer than a page**. The
normal `map` path already handles that: `show`, for a range it does not own,
calls `split(base, len)` before mapping. The pin now does the same, and the
practically-identical failure count went from 45,740 with a 2.2 fps collapse
to **3** mapping refusals out of the whole startup.

Those three are still 487, at addresses that were presumably cut loose by an
unmap between the note and the touch. That is the remaining piece: the
placeholder a note relies on has to be one nobody else can split away, which
means the note has to own its page's placeholder from the moment it is noted
(split it then, not on the fault).

### Fifth try: it runs. It is also 27 times slower.

Two changes made it survive a whole startup: the page is cut out of its
placeholder at note time (`split(to + k, PAGE)` beside the note, where the table
is already held and nothing else maps there), and a refused mapping is not a
failure if something is committed at the address already -- the title mapped
that page itself in between, and a second view of the same page changes
nothing.

    could not be mapped: 0     breakpad: 0     fps: 29.9 -> 1.1

So the mechanism is real end to end: noting, reading through the pin, faulting,
mapping from the section, letting go. What it is not is fast. 909 ms a frame
says the pages are being touched almost as fast as they are noted, and each
touch costs a fault, a split, and a kernel mapping -- worse than the batch the
note replaced.

The next measurement is already built into the counters: `soft::counters()`
gives noted, made real, let go and bytes read. If made-real is close to noted,
soft views cannot help on this title at all and the switch should be dropped
rather than tuned. If noted is much larger, the fault path is what costs, and
it is worth making the fault cheaper before believing any of it.

## Why the soft views are gone

Reverted in `41b5d7a`. The port cost five run cycles and ended in the one place
that does not get argued with: it drew the wrong picture. With
`VICTORY_SOFT_VIEWS=copies` parts of the scene were simply not there, and the
frame time went from 40.2 ms to 54.0 (18.5 fps), once 909 ms. A saving that
both loses content and costs time is not a tuning problem.

What stays is the measurement it grew out of: `map_alias` and `map_aliases`
log `slow page mapping call` for anything over 50 ms, and one 60 s startup run
produced seven of them, the worst 214 ms for 3,693 pages (58 us a page of
kernel time). That is where this branch's stalls live, and it costs nothing
measurable.

What was learned, for whoever walks this road again in this tree:

- the title reads title memory while holding `PHYSICAL`, so a maker thread
  parked on a latch cannot help the faulting thread (that was three deadlocks
  in one run);
- a noted range at these addresses is `MEM_RESERVE|MEM_PRIVATE`, a slice of a
  7 GB reservation, and the placeholder holding it is longer than a page: the
  page has to be cut out (`split`) at note time, not on the fault;
- a page mapped by someone else between note and touch is not a failure;
- and even with all of that, the pages get touched about as fast as they are
  noted, which is why the arithmetic never worked out.

## Where the 58 us a page actually goes

The mapping timer from the section above now splits its own time in two, and
reports both per page on every call over 50 ms (`kernel_us_a_page`,
`ours_us_a_page`):

| call | pages | kernel us/page | ours us/page |
| --- | --- | --- | --- |
| 383 | 36 of them newly mapped | 235 | 4 |
| 486 | 486 | 105 | 3 |
| 1,986 | 1,986 | 25 | 2 |
| 1,809 | 1,764 | 67 | 1 |
| 1,136 | 1,134 | 71 | 1 |
| 724 | 436 | 85 | 2 |
| 154 | 147 | 414 | 4 |
| 86 | 50 | 480 | 6 |
| 172 | 172 | 327 | 4 |
| 275 | 235 | 313 | 5 |

The kernel's `MapViewOfFile3` is the whole bill: 25 to 480 us a page. What we
do around it - noting the bytes to the GPU side, the read-write notice, the
in-place census - is 1 to 6 us a page, and that is with the notes in place.

One more thing the numbers show: two calls spent 50 and 62 ms inside
`map_aliases` with **nothing** mapped at all. That time is the placeholder
splitting and the unmapping, not the mapping. So the next thing worth measuring
on this path is `split()` and `unmap()`, which have never been timed.

That closes the soft-view question for good: the 58 us a page was never ours to
save by doing the bookkeeping differently. The only lever is not calling the
kernel, which is what soft views were for, and they painted wrong.

## The four system calls, counted

The streaming log (`VICTORY_DSTORAGE_LOG=<file>`) already counts the mapping
calls by kind; a bench run with it on, 123 seconds of samples:

| syscall | calls | ms in all | share of the four | per call |
| --- | --- | --- | --- | --- |
| `UnmapViewOfFile2` | 107,603 | 6,333 | 59.2% | 59 us |
| `MapViewOfFile3` | 222,076 | 3,964 | 37.1% | 18 us |
| `VirtualFree` (split) | 153,494 | 360 | 3.4% | 2 us |
| commit | 10,716 | 35 | 0.3% | 3 us |

199,071 mapping calls over 301,801 pages in 123 s: 44 us a call, 29 us a page,
8.8 s of call span in 123 s of wall clock (about 7% of the streaming thread,
but it is the thread the frames wait for).

Two things this changes:

- **Unmapping is the bigger half, not mapping.** 59 us an unmap against 18 us
  a map, and half again as many unmaps as maps. Every page the title recycles
  its pool for is mapped and unmapped twice (once into its pool, once into the
  GPU's tiled heap), and the unmap is the expensive half.
- **The split is not the cost** - 2 us a call - so `VICTORY_MAP_LEAN` is
  already doing the right thing and there is nothing left to win there.

Our own work around the calls stays at 1 to 6 us a page, so on this path there
is nothing of ours left to shave: the cost is the kernel's per-call bill, and
the only lever is the number of calls, which is the title's own streaming.
Which makes the mapping thread count the one knob worth measuring again: if a
call is 59 us of waiting for the process's address space lock, more threads
than one may overlap that wait.

## VICTORY_QUICK_FIND: on by default was a loss, so it is off

The fork keeps a per-thread memory of what each ask for a buffer's host copy
found (`shadow.rs`, `FOUND`), on unless `VICTORY_QUICK_FIND=0`. Measured on this
PC, two alternating runs of 25 s in the world (on, off, on, off):

| arm | run 1 | run 2 | mean |
| --- | --- | --- | --- |
| on | 53.9 ms | 47.8 ms | 50.8 |
| off | 51.9 ms | 46.5 ms | 49.2 |

On costs 1.6 ms a frame (+3.4%), and both pairs fell the same way. The asks go
through a read lock five threads may hold at once and hit the map's first
nodes, so the hash and the thread-local it saves little. The default is now
off; `VICTORY_QUICK_FIND=1` brings it back.

## Where the frame goes now (same runs)

    48.7 ms = preparing 29.0 + copying back 16.2 + the card 0.0
    preparing 29.0 = copies 9.1 ms / 55.5 MB + textures 0.8 ms / 29.8 MB

The 19 ms of preparing that no meter names is not ours: a 1 ms sampler

| --- | --- | --- | --- |

| 1920x1080 | 38.8 ms | 42.7 ms | 40.8 |

| base | 47.7 / 46.2 ms | 31.2 / 31.9 | 10.9 / 66 MB | 18.3 / 20.5 MB |

Two things fall out:

- **The copying back is what shrinks** - 20 MB to 11-12 MB, 18 ms to 12 ms -
  because shaders write half the bytes into title memory at 720p. The copies
  barely move and the preparing does not move at all. So this is not "less
  work for the card" (the card is idle either way here), it is fewer bytes
  landing.
- **2560x1440 as an output size is a trap.** Its copy-back is the cheapest of
  all (10.7 / 12.3 MB), and yet the frame is worse, because the preparing goes
  to 46.6 ms and once to 174.6 ms: 1707x960 is a fractional scale the title
  handles badly. Not worth chasing; the mode is simply not to be offered.

It is not in `run-tuned.bat`, which keeps the old shape: it has a launcher of its own, `run-tuned-1080.bat`, so the two can be run side by side without editing anything, and their logs do not land in the same file (`memtrim.log` against `memtrim-1080.log`). The price is
the picture: 1280x720 rendered and upscaled, not 2560x1440. `VICTORY_OUTPUT`
unset goes back. A benchmark arm that wants to compare against the old shape
passes it back itself: `-Extra @{VICTORY_OUTPUT='2560x1440'}` is the trap, so
the control is simply no `VICTORY_OUTPUT` at all (3840x2160 settings).

## What the other forks' issue trackers did and did not give

`Marvisak/VIctory#3425` keeps a per-part frame budget (553 to 223 ms frames on
an RTX 5090 under Wine) and its CPU table names the same first two items ours
does: copy-back of marked pages (50.7 ms for 2,813 pages / 101 MB) and refresh
change checks (23.9 ms). Its copy-back PRs (#3246, #3320, #3343) aim at what we
already do: read back marked pages, not whole declared ranges - which is why
101 MB costs them 50 ms and 16 MB costs us 16 ms. One of them (#3341) measured
**slower** by 5 to 7 ms in two independent pairs, so "make copy-back cheaper"
is a direction that easily goes backwards.

Its largest item no PR touches is descriptor heap mirroring
(`HostHeap::sync_slots`, 384k slots, 18.1 ms). We measured ours: 13.04 ms of
work a frame (157,846 slots looked at, 10,273 records mirrored), but **0.66 ms
of it is waited for** - it runs on `victory-heap-sync` beside the preparing
(`VICTORY_HEAP_SYNC_ASIDE`), so 12 ms of it is already hidden and there is
nothing to win there.

Where our 16 to 18 ms of copying back actually goes, from the landing meter
that was already there (`landing per frame`, four threads): merging what was
fetched 8.94 ms (24.92 ms over the threads, 251 jobs), read-backs and lists
5.40 ms, looking through copies 4.08 ms, which pieces to fetch 1.49 ms, merging
the others 1.49 ms. Of the threads' time, 5.62 ms goes to opening or noting
guards. The volume is 19.5 MB, so the throughput is about 2 GB/s - a fifth of
`memcpy` - because 1,118 pieces scatter over 9,674 pages of 4 KiB with the
guard opened per 32-byte block. That, not the byte count, is the next thing to
try there.

`LooperSalty/AnyXboxX` is an Xbox Series X emulator with VIctory in
`third_party/victory`; its own roadmap calls "copies and read-backs between the
console's memory and the PC's" the main CPU cost, and reports about 24 fps
median in the world at 1080p on an RTX 4070 SUPER (30 fps only up to about
4,000 draws), which is where we are at 5,942 draws. The one lever it uses that
we had not is the output size above.

`xcl-dev/xcl` is a different lineage (a recompiler and its own runtime), and
its issues are loader, shader-compile and correctness ones: nothing for the
copies or the copy-back.

## PR #477 `VICTORY_WC_NO_BACK=1`: the copy-back is nearly gone

The biggest single item this fork has found so far is not ours: `Belobug` PR
#477 (branch `icecreammule277-dot:wc-no-back`, based exactly on `4eb6cfd`)
leaves shaders' writes into write-combined title memory on the card. They are
not declared as written, so there is no snapshot, no compare and no copy-back.
Ranges of 64 KiB or more that lie wholly in write-combined memory, whose copy
is in the card's journal and known to be watched, are the ones left; everything
else is copied back as before.

Merged here (one conflict, a `census::tag()` line in `host.rs`), both launchers
set it. Measured on this PC, one session, arms alternating, heavy frames only
(5,500 draws or more, medians):

| arm | heavy frames | frame | copies up | copying back |
| --- | --- | --- | --- | --- |
| base | 54.9 / 51.6 ms | 53.3 | 10.1 / 63 MB | 18.1 ms / 22.8 MB |
| `WC_NO_BACK=1` | 41.1 / 46.0 ms | 43.6 | 7.0 / 34 MB | 5.7 ms / 1.1 MB |

So **-9.7 ms on heavy frames (-18%)**, and the work behind it: copying back 18.1
to 5.7 ms and 23 MB to 1.1 MB, copies up 63 to 34 MB, preparing 31 to 23 ms.
On light stretches the title's own 30 fps cap (33.3 ms) hides the gain - one
`WC_NO_BACK` run sat at 34.7 ms with 4,844 draws, where nothing can show.

The PR's own numbers agree (7900 XTX: 78.6 to 67.7 ms, copy-back 34.8 to 17.2 ms)
and a 7800 XT + 9800X3D report puts it at 28.6 to 30.0 fps, inside the cap.

What it does not cover, from the PR and its census: about 20% of the ranges
cannot be guarded (read-only guard blocks, memory not committed); a read after a
write to the same page within one second is not seen; and one tester saw a dark
shirt once in five runs. The census over 13 minutes counted 0 page reads of the
ranges left on the card, so the title does not read them in that scene.

## PR #443 (EXACT and LOOSE locks) measured, and dropped

`wesneyalcantara-lang:locks-and-same-mappings` takes `shadow::EXACT`'s mutex
wait of list threads from 20.5% to 0-3% and `shadow::LOOSE`'s from 11-16% to
0-1%, and skips a page mapping that would show the page it already shows
(`VICTORY_MAP_SAME=0` to turn that off). Merged on top of #477, three runs
against two control runs of the #477-only build right beside them:

| build | heavy frames | frame |
| --- | --- | --- |
| #477 only (control) | 48.0 / 45.0 ms | 46.5 |
| #477 + #443 | 46.2 / 48.2 / 48.9 ms | 47.8 |

Nothing to be had: the contention #443 fixes lived in the copy-back path that
#477 has just removed, so the lock waits it shortens are no longer on the frame.
The merge was reset; the tree is `8e435d6` (the #477 merge) and nothing else.

## 1080p output and VICTORY_WC_NO_BACK do not combine

With `WC_NO_BACK` on, the resolution win of the earlier section reverses. Same
session, arms alternating, heavy frames only:

| arms | frame | preparing | card | copying back |
| --- | --- | --- | --- | --- |
| 4K output (renders 2560x1440) + WC_NO_BACK | 50.8 / 48.8 ms | 25.0 / 24.8 | 5.7 / 5.4 | **1.3 / 1.3 ms** |
| 1920x1080 output (renders 1280x720) + WC_NO_BACK | 51.8 / 54.9 ms | 35.4 / 34.9 | **20.5 / 21.2** | **18.5 / 21.6 ms** |

At 720p the copying back comes back - 1.3 to 18-21 ms - and the card's time
triples. It is not the 64 KiB floor: dropping `VICTORY_WC_NO_BACK_MIN_KB` to 16
or 8 KiB does not restore it (17.6 ms of copying back at 8 KiB, 46.8 ms frame),
so the ranges declared at 720p simply do not end up left on the card the way
they do at 1440p. `run-tuned-1080.bat` carries the numbers and says not to use
it; `run-tuned.bat` stays the one to play.

What is left on the frame at 4K output with `WC_NO_BACK`, from the same logs:
preparing 25 ms (copies 7.3 of 33 MB, textures 0.9), copying back 1.3 ms, the
card 5.5 ms, and about 17 ms that no meter of ours names - the title's own work,
where the 1 ms sampler put 24.7% of a frame before. So the copy-back chapter is
closed: what remains of it is one and a bit milliseconds.

## Where the unnamed 17 ms goes, re-sampled under WC_NO_BACK

One window (95-120 s of the run, every 1 ms, 15,652 samples) with the build that
has `WC_NO_BACK` on. The sampler's own summary puts 38.2% of all samples on one
site, and the frames under it are the title's:

| samples | share | stack (innermost first) |
| --- | --- | --- |
| 4,068 | 26.0% | `ntdll+0x166464` < `KERNELBASE+0x1427f` < title `+0x221c3c2` |
| 1,568 | 10.0% | `ntdll+0x166464` < `KERNELBASE+0x1427f` < title `+0x43c421e` |
| 165 | 1.1% | `ntdll+0x166464` < `KERNELBASE+0x1427f` < title `+0x43c3d5d` |
| 130 | 0.8% | `ntdll+0x166464` < `KERNELBASE+0x1427f` < title `+0x56a0d` |
| 321 | 2.1% | `ntdll+0x166464` < `KERNELBASE+0x1427f` < `victory.exe+0x6e1175` (relay) |
| 27 | 0.2% | `ntdll+0x166464` < `KERNELBASE+0x1427f` < `victory.exe+0x7b569e` |

`KERNELBASE+0x1427f` is `WaitForSingleObject`. So the title's main thread is
blocked in a plain wait, in its own image, not in any hook of ours: no frame of
any victory module appears anywhere in the eight-deep stack of either site. Its
workers are the ones doing the work - one unnamed thread runs in
`title+0x4fb0c03`, and several others spend most of their samples in the same
`KERNELBASE` wait, i.e. the title is running its own job graph and its main
thread is waiting for it.

That is the same answer the pre-`WC_NO_BACK` sampler gave (24.7% at
`+0x221c3c2`, 10.2% at `+0x43c421e`); removing the copy-back moved no part of
this. Our own threads' waits are small at this site: relay 321 samples, the
submit thread 27. The remaining 17 ms is the title's CPU work, and the only way
to shorten it is to give the title fewer jobs - which is what the copy-back work
already did.

## FSR 4.1.2 at 1920x1080: it works, and it buys 0.3 ms

DexNom's PC FidelityFX bridge is already in this tree (`victory-hle`'s
`fidelityfx.rs`, `apps/victory/src/fsr_4k.rs`, ported from DexNom commit
`ab34a8b`), so nothing had to be written; the only missing piece was AMD's
signed provider. Put `amd_fidelityfx_upscaler_dx12.dll` (57,664,272 bytes,
SDK 2.4.0 `Kits/FidelityFX/signedbin`, blob `6d01d9f5`) and its siblings from the
same folder in `D:\victory-data\fidelityfx-4.1.2`, then set
`VICTORY_FIDELITYFX_DIR` and `VICTORY_FSR_4K=performance|balanced|quality`.
The presets render 1920x1080, 2258x1270, 2560x1440 for a 3840x2160 output.

Two things learned the hard way: a partial provider folder fails to load with
`0xC000007B` - the whole signedbin set has to be there; and a mirror-served
`amd_fidelityfx_upscaler_dx12.dll` can be the wrong build (37,714,951 bytes,
which loads nothing) - check the size, `git hash-object` against the SDK blob
if in doubt.

Same session, arms alternating, heavy frames only, with `WC_NO_BACK` on both:

| arm | n | frame | preparing | copies | copying back |
| --- | --- | --- | --- | --- | --- |
| base (title's own upscaler, 2560x1440) | 9 | **43.8 ms** | 24.6 | 8.4 ms / 39.8 MB | 5.2 |
| FSR 4.1.2 performance (1920x1080) | 9 | **43.5 ms** | 22.1 | 7.6 ms / 36.8 MB | 4.7 |

-0.3 ms, 0.7% - inside the noise this bench has between arms. The log confirms
the work happened: provider "4.1.2", context `render=[1920, 1080]
output=[3840, 2160]`, the dispatch recorded with those extents. Lowering the
render size did what it should to the numbers around it (preparing -2.5 ms,
copies -3 MB, copying back -0.5 ms) and the frame still did not move, because
the frame is the title's CPU work and the card was never the limit (5.2-4.7 ms
of card time). FSR here is a quality choice - a better upscaler at the same
render size in `quality`, or 1080p->4K in `performance` - not a speed one.
