# Tuned run: what was measured (2026-11-27)

One PC: Ryzen 7 9800X3D, 32 GB RAM, Radeon RX 7900 XTX 24 GB, Windows 11
build 26300, Series X profile at 1080p output, ray tracing off. Builds are
`cargo build --locked --profile diag -p victory --features diagnostics`.
Every run is the same sequence from a cold start, 6-10 minutes, and the
figures are of the `host: … fps, … ms/frame` line the runtime prints.

Scenes are not identical between runs; read differences under about 5 % as
nothing. The numbers below repeat across runs, which is why they are kept.

## Where the time went

| Build and settings | p50 frame | p50 fps | p90 frame |
|---|---|---|---|
| original tree, default switches | 59.0 ms | 17.0 | 103.3 ms |
| + the memory patches of this branch | 58.3 ms | 17.4 | 72.5 ms |
| + the renderer port switches (below) | **46.2 ms** | **21.9** | 86.6 ms |

The port switches are the ones `README.md` lists as off by default while
they are tested. Turning them on is worth about 15 ms a frame, more than
every memory patch in this branch together. In the log the preparing
thread goes from 42-52 ms to 28.9 ms a frame: `VICTORY_PORT_CBV` removes
about 22,000 constant-buffer fills a frame, `VICTORY_PORT_GUARD` takes the
title threads' guard waits from 29 ms to about 2 ms, `VICTORY_PORT_JOURNAL`
takes the submit thread's waits from about 6 ms to 0.3 ms.

`scripts/run-tuned.bat` starts the title with them on.

## What was tried and refused

Each was applied on top of the winning tree, built, and run the same way.
All three are worse here, whatever they win elsewhere:

| Change | p50 frame | p50 fps |
|---|---|---|
| Belobug #443 + #451 (exact/loose lock contention) + #393 (tiled mip row runs) | 53.8 ms | 18.6 |
| Belobug #394 (32 GB switch set) + avatarmanz #391 (`VICTORY_WINDOWS_BAR_PCT`) | 51.5 ms | 19.4 |

A first attempt that also carried #393 and #374 in the same commit as the
eleven memory patches measured 8-15 fps; both were dropped, and the
patches are only added to the tree after a run in this table.

## Pipelines made ahead of a run

A pipeline the driver has not seen costs 2.7 ms at the median to make but
533 ms at the p99, and that lands in the game as one long frame. One
recording run (`VICTORY_PIPELINE_BOOK=1`, five minutes) wrote down 3,780
pipelines that had been drawn with; `victory warm --used` made them in
26 s of wall time and 82 s of compiler work, nothing else. The run after
it built **none** while playing, where the run before had up to 176 of
them in flight, and the log's `being made` counter stayed at 0.

It does not move the steady frame time: what is left of a 46 ms frame is
the submitting thread, not compilation. What it removes is the tail - the
single 400-570 ms frames that a first visit to new geometry produces.
Coverage is only what a run has recorded, so a part of the title played
for the first time still compiles as it goes: run `scripts\warm-tuned.bat
record` once there, which plays a run with the book on and then warms.

`scripts\warm-tuned.bat` does both, with the same switches as
`scripts\run-tuned.bat` - the cache is keyed by a pipeline fingerprint
(`e9cc66c4ece2c90a` here), so warming under different switches fills the
cache with pipelines the next run will not ask for.

## 60 Hz

`VICTORY_FRAME_INTERVAL_MS=16.667` does what it says: the menus and videos
reach 55-60 fps (best frame 16.7 ms) and the log confirms the clock is
adjusted (`our clock 16.667 ms; the title's rate 60 … it asks for 16667 us
at 60 Hz`). In the world it costs about 9 ms a frame (median 55.4 ms
instead of 46.2), because twice as many submissions queue on the one
submitting thread. Not used by `scripts/run-tuned.bat`.

## Memory

The eleven patches in this branch reclaim idle upload memory and cap the
texture store; on this 32 GB PC the peak private bytes went from about
38 GB to about 36-37 GB, and the p10 frame improved from 9.7 to 13.8 fps
(fewer long stalls). The pressure thresholds these checks use are only
reached when the machine is short of RAM, so a 32 GB box shows much less
of the effect than the 16 GB reports in the pull requests.

The eleven, all from `Belobug/VIctory-Belobug-AMD` with `base=a-publier`:
#386, #404, #373, #372, #375, #359, #287, #409, #413, #401, #407.

## The benchmark that makes these numbers judgeable

Free runs are not comparable: the same settings gave 40.7 ms one run and
49.1 ms the next, and the same settings drifted 2.4 ms between sessions
(43.1 one session, 40.7 the next). `bench.ps1` and `pad-replay.py` (in
`D:\victory-belobug`, not in this repository) fix that:

- every run launches the title, waits 15 s, presses A on a virtual Xbox pad
  (ViGEmBus) to leave the menu, and waits for the world: frame lines with
  1500 or more draws, twice in a row;
- then it plays the same 10 s input cycle (walk 3 s, stand 1 s, pan right 2 s,
  walk and pan 3 s, stand 1 s) for a whole number of cycles, and takes only
  the frame lines inside that window;
- three runs of one arm spread 1.2-1.7 ms, so an effect has to be larger
  than that to be worth anything;
- arms are compared *inside one session*, alternating (A, B, A, B): session
  drift is larger than every effect measured here.

## Screened and refused (interleaved pairs, 60 s window, same session)

| arm | frame ms | vs base |
| --- | --- | --- |
| base (this branch's launcher set) | 39.0 | - |
| `VICTORY_LAND_THREADS=8` | 41.3 | +2.3 (worse; earlier "gain" was session drift) |
| `VICTORY_WIDE_BACK=0` | 41.8 | +2.8 (worse) |
| `VICTORY_EXACT_BACK=0` | 61.4 | +22.4 (much worse: copies 58 -> 100 MB) |
| all five `VICTORY_PORT_*` off | 51.1 | +10.7 (the ports are worth 26 %) |
| `VICTORY_CARD_BUFFERS=1` | 40.9 | +0.4 (nothing) |
| `VICTORY_JOIN_PARTS=16` | 41.5 | +1.1 (worse) |
| `VICTORY_CARD_AWAKE=0` | 41.2 | -2.3 in one session, +1.1 in the next: nothing |
| `VICTORY_THIN=0` (this also turns the async submit off) | 59.4 | +18.2 |

What `VICTORY_THIN=0` shows is worth keeping in mind: it *lowers* the
preparing time (29.4 -> 24.8 ms) and the copies (10.0 -> 7.8 ms) and still
costs 18 ms a frame, because the submissions then wait for the card on the
title's thread. (No line printed it: the async submit line does not print
when it is off: look for "submissions prepared by a thread of ours".)

## Ported from Yaekai/victory-scarlett-3070, and what came of it

`VICTORY_CARD_LISTS=1` (foxhound 441446d, through that fork's bc264a4): the
copies in the card's memory whose CPU side changed are taken from a list made
as they are touched, instead of being found by a walk over every copy
(`crates/victory-gpu/src/shadow.rs`: `carded`, `TOUCHED`, `card_dirty_listed`).
Off by default.

Measured: frame 43.8 vs 43.1 ms (-0.6, inside the noise), copies 10.0 vs
10.1 ms. The list does what it says (the touch list is walked, not the whole
table), but the walk was never the cost: this branch's own counter line shows
95 hash passes over 415 pieces on the plain path, not the 348 over 2,080 seen
in an earlier, heavier scene. Left in the source, off, like that fork's other
"built, exact, no gain shown" switches.

Read from the same fork and not taken:
- `VICTORY_WINDOWS_BAR_MB` (the title's memory read through Resizable BAR):
  it reports no gain while the card stands idle, plus 1.4 GB of VRAM. That is
  this branch's situation too, so the "copy less by mapping it" road is closed
  before it is walked.
- `VICTORY_LEVELS_ON_DEMAND`: its launcher sets it to 0 and calls it the
  largest single gain (re-uploads 6.4 GB -> 15 MB, about 4 GB less commit).
  This branch is already off by default, which is the same setting.
- `VICTORY_TABLE_MEMO` (81 % of about 54,000 table entries a frame not built
  again) and `VICTORY_TABLE_NAMED_ONLY` (27,000 slots a frame less): both live
  inside a 1,150-line commit over `draw.rs`, far from this tree's lineage. The
  ceiling here is the 3.28 ms a frame the descriptor records cost, so the port
  is worth nothing like its size.
- `VICTORY_SOFT_VIEWS=copies`: the one still worth having. It keeps the views
  the title's batch page-mapping copies make in the layer's books and maps them
  only when touched (264 lines over `shadow.rs`, `resource.rs`, `host.rs`); that
  fork went from 2.7 % to 0.8 % long frames and from 10-12 to 3 five-second
  freezes. This branch's own stall was 4.5 s of preparing, once, followed by a
  removed device.
